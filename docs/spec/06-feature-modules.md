## 6. Feature modules with acceptance criteria

### 6.1 Central repository & tiered disclosure
- **Tier 0 draft** (owner only). **Tier 1 public teaser**: title, niche, region, maturity (idea/prototype/MVP/live), ask (sale/licence/co-build/pilot/hire), **problem statement**, impact claims, ≤150-word summary of *what* the solution does, never *how*. Visible to all signed-in users and to scout agents. **Tier 2 full proposal**: approach, architecture, pricing, demo/repo links, attachments (PDF/PNG/JPG/MD/TXT ≤20 MB, ClamAV-scanned, PDFs re-rendered). Released only when the single server-side predicate `can_view_tier2(viewer, version)` (`proposals/access.py`) holds: `FEATURE_TIER2_ENABLED`; org E2, not suspended; viewer membership on the verified domain with role reviewer|signatory|admin and TOTP enrolled (step-up if last MFA >12 h); Master Enterprise Terms signed (hash recorded); per-person, per-proposal **Evaluation NDA** accepted (template hash logged); an active `disclosure_grant` from the owner's policy (`auto-grant to orgs I tagged` default; `manual approval` otherwise and always for stage-0 `org_agent_match`/`org_browse` interest; optional `any E2 org in my niche`; creating a grant on an untagged proposal consumes a `docs/spec/05-subscriptions-billing.md` unlock); no WITHDRAWN/DECLINED/TERMINATED engagement for that org; no revocation. Tier-2 fields and attachment keys live in `proposal_confidential(version_id, ciphertext, kms_key_id)`, encrypted per proposal; `full_embedding` lives in `proposal_confidential_embeddings`, readable only by `tier2_moderation`. SELECT on these tables is limited to the DB roles `tier2_reader` (request path after the predicate passes, incl. watermarked renders), `provenance_worker` (manifest), `tier2_embed_worker`, `tier2_moderation` (`docs/spec/06-feature-modules.md#63-proposal-submission-tagging--pitch-to-company` Tier-2-vs-Tier-2 job, evidence packs; staff only) and `dsr_exporter`; every read sets subject context and writes an audit event. Policy changes, manual grants and raw-download enablement need a TOTP/passkey step-up and send an email notice. **Tier 3 deal room**: parties to an engagement only, opened by the mutual NDA (`docs/spec/06-feature-modules.md#69-kuccps-style-engagement-tracker-state-machine-single-source-of-truth`).
- Over-disclosure check on the teaser editor: Haiku 4.5 flags algorithm/architecture detail; warns only.
- Before first Tier-2 release: non-blocking nudge about KIPI utility-model/patent filing and KECOBO voluntary registration.
- Tier-2/3 renders are server-side and carry two marks: the **owner attribution** (pseudonymous handle until `INTEREST_CONFIRMED`, display name after; cert id, `registered_at` EAT, QR/link to `/verify/{cert_id}`) and the **per-viewer mark**; Tier-1 cards show the owner handle and cert id. Raw download only if the owner enables it (also marked). Repo links appear only at Tier 2.

- **Browse repo** (every org plan): all Tier-1 teasers, keyword search plus filters (niche, county, maturity, ask, linked Problem).

### 6.3 Proposal submission, tagging & "Pitch to company"
- Proposal editor as a 3-step wizard (Problem & teaser → Full details → Review, attest & publish) with two layers (teaser / full), linked Problem picker **or "Describe a new problem"** (creates a Problem with `source=developer`, labelled "Developer-reported", moderated after publishing without blocking it), niche label (e.g. *ICT › Networks & Telecommunications*), maturity, ask. Publishing registers the version (`docs/spec/06-feature-modules.md#64-authorship-provenance--watermarking-the-honest-watermark`); it is the one primary action.
- Tier-1 fields reject URLs, bare domains, email addresses, phone numbers (E.164, 07xx/01xx) and till/paybill patterns (contact details belong in the deal room); a teaser that names a directory org negatively or describes a security vulnerability is held for moderator approval, and vulnerability content is never public (`docs/spec/06-feature-modules.md#612-admin-moderation--disputes`).
- **"Pitch to company"** button opens a directory picker grouped by niche showing E0/E1/E2 status; a developer can tag several orgs on one proposal (cap per plan). Each tag to an E2 org creates an Engagement in `SUBMITTED`; tags to E0/E1 orgs are held (`held_unclaimed` / `held_pending_verification`). One open engagement or held tag per (developer, org) at a time: tagging that org from another proposal returns 409 with the reason; 30-day cooldown after a decline.
- One-click "Turn this into a proposal" from a connected GitHub repo or from a project the local reminder flags as dormant (v1.1).
- Submission assistant (Sonnet 5) suggests which fields belong in Tier 1 vs Tier 2; runs only after an explicit per-use opt-in recorded as a `consents` row `tier2_llm_assistant` (expires with the session); never auto-publishes.
- Originality check (informational, never blocking, ≤10/developer/day): MinHash LSH (5-word shingles, Jaccard ≥0.8) + bge-m3 cosine ≥0.88 of the submitter's text against **other owners' Tier-1 teasers and teaser embeddings only**; coarse bands, never numeric scores; the Sonnet explainer sees the submitter's text plus others' Tier-1 only. Tier-2-vs-Tier-2 comparison (≥0.95, different owner, later timestamp) runs in a moderator-only job and reaches neither developer except through a dispute.
- Deadlines are those of the `docs/spec/06-feature-modules.md#69-kuccps-style-engagement-tracker-state-machine-single-source-of-truth` table (`backend/config/policy.yaml`); `engagements` is the source of truth, `tags.status` (`docs/spec/06-feature-modules.md#69-kuccps-style-engagement-tracker-state-machine-single-source-of-truth` codes) a projection. Org actions: Approve to proceed (non-binding) (`INTEREST_CONFIRMED`), Decline (reason code), Request info (`INFO_REQUESTED`, clock paused until the developer answers). Expiry drops the responsiveness score. Decline reasons are the `docs/spec/06-feature-modules.md#69-kuccps-style-engagement-tracker-state-machine-single-source-of-truth` `end_reason` codes.

### 6.4 Authorship provenance & watermarking (the honest "watermark")
Do not promise that ideas are "theft-proof": no software can stop idea theft and the Copyright Act 2001 protects expression, not ideas. Build **evidence + controlled disclosure + traceability + a dispute path** (hash + trusted timestamp + NDA-gated access + per-viewer log + evidence pack), which is what helps in a dispute:

1. **Publishing registers the version** (drafts are not evidence): RFC 8785 canonical JSON manifest (all Tier-1/2 fields, attachment SHA-256s, owner refs `SHA-256(subject_salt ‖ user_id)` and splits — names are resolved at render time and certificate PDFs generated on demand, never stored under Object Lock — attestation ids, `prev_version_hash`, optional git commit SHAs) → `content_hash = SHA-256(manifest)` → Ed25519 server signature (key in KMS; public keys at `/.well-known/provenance-keys.json`) → RFC 3161 TSA token (`TSA_URL` configurable; DigiCert primary, FreeTSA fallback; "Timestamp pending" until stored) → OpenTimestamps proof with hourly upgrade job (Release 2) → `proposal.version_registered` audit event. Each step is an idempotent background job.
2. **Authorship certificate PDF** per version: cert id, owners (legal name only if D2-verified), splits, UTC + EAT time, hash, signature/key id, TSA serial, attachment hashes, QR to `/verify/{cert_id}`, fixed footer: *"This certificate is evidence of what was submitted and when. It is not a patent, copyright registration or guarantee against independent development or misuse."* Public `/verify` recomputes the hash from an uploaded file or looks up a cert, showing only hash, timestamp, TSA serial and match/no-match unless the owner opts to show name and title; offline guide covers `openssl ts -verify` and `ots verify`.
3. **Per-viewer watermarking** of Tier-2/3 renders. Release 1: visible tiled overlay + metadata `view_id` + access log. Release 2: invisible marks (meaning-preserving text variants seeded by `view_id`, never touching numbers, code, identifiers or pricing, with the rendered text's SHA-256 mapped back to `content_hash`; image-domain mark). Trace tool is staff-only inside an open dispute and returns candidates with confidence ("probable match", never "proof").
4. **Append-only `audit_events`** with `prev_hash`/`event_hash` chain: payloads hold only ids, enums, amounts and per-subject-salted SHA-256 digests of personal or free text; the text lives in mutable `event_details(event_id)`, so erasure overwrites it without touching the chain. Appends serialised (`pg_advisory_xact_lock(chain_id)`, UNIQUE(chain_id, prev_hash)); app role INSERT/SELECT only; triggers block UPDATE/DELETE/TRUNCATE; migration-only table owner; hourly RFC 3161 anchor; nightly verification publishes a signed Merkle root to `/transparency`.
5. **Prior-knowledge declaration**: within 10 business days of first Tier-2 access an org may declare existing similar work by submitting the hash of dated internal evidence; shown to the owner; "declarations are not recorded on the platform after this window".
6. **Evidence pack** (`docs/spec/06-feature-modules.md#612-admin-moderation--disputes`) with an unsigned Evidence Act s.106B certificate pre-filled with system facts, signed on request by the records custodian named at G2.
7. **Ownership attestations** at each registration (created it / not owned by employer, university or client / no third-party confidential info). Single-owner proposals in Release 1; co-owner confirmation and splits in Release 2 (schema kept).
8. Developer verification: D0 email; D1 phone OTP via `SmsProvider` (Fake + Africa's Talking or equivalent, vendor at G1; required to publish and tag); D2 KYC via `KycProvider` (Fake in CI/staging; `ManualReview` by staff `admin` in Release 1: ID images go to a separate encrypted, non-backed-up `kyc-review` bucket, visible only to that role, never logged, auto-deleted 72 h after the decision; Smile ID or equivalent in Release 2; store only reference, verified legal name, ID type, last 4 digits, `is_adult`, result; **never images**), required for deal room and signing; D3 optional GitHub/KECOBO/KIPI numbers shown as self-reported. Users 18+.

| AC | Criterion |
|---|---|
| AC-IP-1 | Recomputing SHA-256 from the stored manifest equals `content_hash`; the `.tsr` verifies with openssl in the test. |
| AC-IP-2 | Editing one byte of a stored manifest, or any UPDATE/DELETE on `audit_events`, is rejected by trigger or detected by the chain verifier. |
| AC-IP-3 | Release 1: the trace tool recovers `view_id` from a leaked render's metadata and visible overlay and matches it to the access log. Release 2: also from ≥400 copied words and a re-screenshotted page image. |
| AC-IP-4 | Inserting "theft-proof" into any template, i18n string or email body fails CI. |
| AC-IP-5 | A registration attempt without D1 returns 403. |
| AC-IP-6 | "Deleting" a registered proposal hides it but retains manifest, proofs and audit events; the UI states this before confirming. |
| AC-IP-7 | After an erasure outside legal hold, `audit.verify_chain` still passes and no plaintext PII for that subject remains in `audit_events`, `engagement_events` or evidence objects. |
| AC-IP-8 | Closing an engagement whose IP terms are `assignment` appends a provenance event naming the assignee, shown on the certificate and `/verify`, while the original authorship record stays intact. |
| AC-IP-9 | 72 h after a `ManualReview` decision no object remains in `kyc-review` for that subject, and no image key appears in logs or `audit_events`. |

### 6.6 Trending problems & trending projects
- Score `T(t) = Σ w_e · 2^(−(t−t_e)/h)`, h = 14 days (problems), 7 days (projects); displayed as per-niche z-score against a 90-day baseline so small niches can trend.
- Problem weights: verified-org brief posted 6; new official source 5; matching tender 8; new independent source 3; proposal submitted against it 2; scout match 2; developer save 1. Project weights (**verified-org actions only**): intro/info request 12; shortlist 8 (a reviewer's org-internal flag on an engagement, no state change); verified view 3.
- Anti-gaming: unique verified accounts only, 1 event/account/item/day, no self or same-org boosts, burst detector (>50% events from accounts <7 days old are ignored), ≥3 distinct actors before "Trending" shows, Wilson lower bound for ratios. Cold start: until the baseline and actor thresholds exist, show "New this week" and hide the badge; project badges never show org counts or names.
- **Opportunity Gap** view: problems in the top trend decile with <3 proposals. Trending Projects are always shown beside the Problem they solve; a project card links to its problem and vice versa.
- Badge explains itself: "Trending in Telecom · Kenya: 2 new tenders, 4 companies scouting".

| AC-TREND-2 | Every Trending Project card renders its linked Problem; the Opportunity Gap list contains only problems with <3 proposals. |

### 6.7 Personalisation ranker ("what to pursue")
- **MVP ML = bge-m3 semantic fit inside a transparent hybrid score**; the learning-to-rank pipeline below is built in Phase 5 and activated only at the data thresholds. Features normalised to [0,1] (z-scores clipped to ±3, logs as `min(1, x/log(1+cap))`), `score = 100·Σw·f / Σ|w|`, weights in `ranking/weights_v1.yaml`: f1 semantic_fit (bge-m3 cosine, developer profile + summaries of their last 5 published proposals and any imported repos vs card) 0.25; f2 niche_match (liked 1 / adjacent 0.5) 0.15; f3 region_match 0.08; f4 skill_coverage 0.12; f5 trend z-score 0.10; f6 evidence_confidence 0.08; f7 market_pull `log(1+scouts+tenders+briefs)` 0.10; f8 crowding `log(1+proposals)` −0.07; f9 track_record `(done+1)/(started+2)` per niche 0.07, counting the developer's own platform proposals and engagements (published or engaged = started, CLOSED = done) plus the **opt-in** GitHub import (started = owned repo with ≥10 commits; done = release/tag, archived or user-marked completed; repo niche = argmax bge-m3 cosine of README/description vs niche descriptions, threshold 0.5) and, Release 2, local reminder stats; f10 freshness `2^(−age/30)` 0.05.
- MMR re-rank (λ=0.7), ≤3 per niche in top 10, 1 exploration slot in 10 labelled "Exploring". Labels: Strong fit ≥80, Good fit 60–79, Stretch <60. **Pursuit recommendation** (the honest answer to "worth pursuing"): `Pursue / Consider / Not now`, computed in code from market_pull, trend, crowding, evidence confidence and fit, always with ≥1 reason. **Never "profitable" or revenue predictions.**
- "Why" chips (top-3 positive contributions) and "Why not" chip (top negative), generated in code (card chip limit: `docs/spec/07-ux-information-architecture.md`).
- Cold start: onboarding requires 3–5 liked niches, region, stack; f1 and f9 are active from day one whenever imported history exists; only interaction-derived signals wait for 20 interactions; new cards get +0.05 for 7 days.
- Log impressions `(user_id, item_id, position, ranker_version, surface, ts)` and outcomes (click, dwell ≥20 s, bookmark, draft_started, submitted, company_intro) plus explicit thumbs with reason codes from day 1.
- LightGBM LambdaMART pipeline (feature/label logging, training script, IPS position-bias correction, offline NDCG harness, shadow scoring behind a flag) built in Phase 5; activated only at ≥5,000 labelled impressions, ≥500 positives, ≥200 active developers, offline NDCG@10 ≥ +5% and interleaving non-inferior on draft_started; SHAP explanations; hybrid stays as fallback. Profiling has an opt-out toggle (DPA s.35).

| AC-PERS-1 | A brand-new developer with 3 liked niches and a county receives a non-empty, explained list. |
| AC-PERS-2 | Every recommendation row stores its feature vector and shows the pursuit chip plus ≥1 "Why" chip on the card at 360 px; "profitable" and revenue figures never appear; a card with crowding ≥10 proposals and market_pull 0 is never "Pursue". |

### 6.8 Enterprise scout agents & email digests
- **Form, not prompt-writing**: niches (≤5), regions/counties, include/exclude keywords, budget band (KES), maturity[], exclusion rules, `min_fit` (0–100, default 60), frequency (daily/weekly/on_new, per plan), recipients (Reviewer-role members on the verified domain, capped per plan, editable by an org admin), language (en/sw). Configured from Inbox › Scout matches. Live **Preview matches (last 30 days)** before saving. `entitlement_tier` read from the subscription, not editable.
- Pipeline (incremental cursor; scout DB role has no grant on `proposal_confidential`: **Tier 1 + metadata only, never Tier 2**): SQL hard filters → bge-m3 top-200 → Haiku 4.5 screen to top-50 → Sonnet 5 rubric `FitAssessment{relevance, feasibility, strategic_alignment, evidence_strength, maturity_fit (0–20 each), rationale ≤80 words, quoted_spans[], risks[], questions[]}` for ≤15 → `final = 0.6·deterministic + 0.4·LLM` on 0–100, where deterministic = 50·cosine + 30·(niche/region/maturity/budget match) + 10·tagged-this-org + 10·evidence (`matching/weights_v1.yaml`) → digest ≤10 items rendered **by code from a fixed template with escaped fields**; any URL, domain, email or phone in quoted text is defanged (`example[.]com`) with data detectors off. Daily/weekly runs via Message Batches, `on_new` via the sync API; system prompt/rubric/profile prompt-cached.
- Digest links open authenticated pages; **nothing changes state on GET**. Feedback ("Not relevant: reason") tunes `min_fit` ±5 after 5 consecutive signals; suggested exclusions shown to admin for approval.

### 6.9 KUCCPS-style engagement tracker (state machine, single source of truth)
One engagement = one proposal × one org (`docs/spec/03-glossary-roles.md`). The state machine lives in `engagements/state_machine.py` as a transition table, the **only** definition of stages and deadlines (values in `backend/config/policy.yaml`); UI stepper, API guards, role matrix, reminder rules and notification dispatch are generated from it. **Dual-endorsement stages** (KUCCPS analogue: Developer = releasing party, Enterprise = receiving party): 0, 4, 5, 8, 11, 12, `TERMINATED`, and each milestone acceptance and payment confirmation. Rendering: 5-group stepper (Review · Contact & NDA · Agreement · Implementation · Close), sub-stages collapsed except the current group; vertical on mobile, horizontal spine + detail panel on desktop; chips ✓ Completed · ● Current · ○ Pending · ⏸ On hold · ⚠ Overdue · ✕ Ended; each stage shows status (icon + text + colour), actor, timestamp (`23 Sep 2026, 14:05 EAT`), next action, "Awaiting: <party>", due countdown. "Whose turn" banner pinned; the action button appears only for that party. Dual-endorsement stages render rows **Endorsement by Developer** / **by Enterprise** (status, name, role, time, method). BD = Kenyan business days (weekends and gazetted holidays excluded via an admin-editable file).

**Main path**

| # | State | Label | Entered by | Next actor | Due rule | Notif. |

**Milestone sub-tracker** (inside 9, repeats M1..Mn): `PLANNED → IN_PROGRESS → SUBMITTED_FOR_REVIEW → ACCEPTED | CHANGES_REQUESTED(→IN_PROGRESS)`; review due = agreement window (default 5 BD), reminder at 3 BD, escalation at 5 BD; deemed acceptance only if the signed clause says so; optional `PAYMENT_DUE → PAYMENT_RECORDED (org) → PAYMENT_CONFIRMED (dev)`.

**Side branches** (banner on the stage where they occurred, never extra steps): `DECLINED` (org reason code, or `BY_DEVELOPER` from stage 0), `WITHDRAWN` (developer, before agreement; Tier-2 access revoked), `EXPIRED` (system), `ON_HOLD` (reason + resume date ≤60 days; after agreement requires acknowledgement by the other party within 3 BD else `DISPUTED`; due dates shift by hold duration), `DISPUTED` (category, statement, evidence; due dates frozen; mediator assigned ≤2 BD; outcome resume / `TERMINATED` / `CLOSED`), `TERMINATED` (dual endorsement or mediator outcome; summary of work accepted, amounts paid, IP position), `INFO_REQUESTED` (org asks from 1–2, developer answers, clock paused).

**Codes.** `engagements.origin` ∈ {`tagged`, `org_agent_match`, `org_browse`}. Terminal states: `DECLINED`, `WITHDRAWN`, `EXPIRED`, `TERMINATED`, `CLOSED`. `end_reason`: DECLINED → {NOT_PRIORITY "not a current priority", ALREADY_IN_PROGRESS_INTERNALLY "already solved internally" (**requires internal start date + attestation checkbox, stored immutably and shown to the developer**), BUDGET, NOT_RELEVANT, NEEDS_MATURITY, OTHER (≥20 chars), BY_DEVELOPER}; EXPIRED → {NO_REVIEW, NO_DECISION, CONTACT_NOT_MADE, NO_DEV_RESPONSE}. `tags.status` ∈ {held_unclaimed, held_pending_verification, delivered, withdrawn, expired, released}.

**Instruments per stage:** ToS + AUP (account) → Master Enterprise Terms (onboarding, signed by the org Signatory; evaluation-only, no residuals clause, member NDA acceptances bind the org, MET prevails over uploaded NDAs and unsolicited-submission policies, Tier-1 teasers are non-confidential, non-circumvention, audit-logging consent, Kenyan law) → Evaluation NDA (per proposal, per person; Tier 2) → Prior-knowledge declaration (optional, 10 BD) → EOI (non-binding) → Term sheet (binding only for confidentiality/exclusivity) → Mutual NDA (Tier 3) → Definitive agreement → Milestone confirmations → Acceptance certificate. `SignatureProvider` adapter: Release 1 internal simple e-signature (signer identity D2 or org Signatory, TOTP/passkey step-up — SMS OTP only as fallback with 24 h delay and notice to the other party — IP, UA, UTC time, SHA-256 of final PDF, PAdES seal, RFC 3161 stamp, `doc.signed` audit event) only for ToS, MET, NDAs, EOIs, milestone confirmations and the acceptance certificate. Agreements with IP terms `assignment`/`exclusive licence` or referencing a patent/utility model (Copyright Act s.33, KICA s.83P) use a CA-licensed E-CSP advanced e-signature (Release 2) or **"Signed outside the platform"** (both parties upload the wet-ink/advanced-signed PDF, endorse that it matches, hash stamped). `docs/legal/esign_exclusions.md` (advocate, G2) lists blocked document types; until then powers of attorney, wills, negotiable instruments and land documents are blocked. All templates are lawyer-reviewed, versioned and hashed; **no LLM-generated contract text at runtime**.

**Persistence:** `engagement_events` append-only, hash-chained (`hash = sha256(prev_hash ‖ canonical_json)`, PII rules as `docs/spec/06-feature-modules.md#64-authorship-provenance--watermarking-the-honest-watermark` item 4), INSERT-only via trigger and grants; `engagements.state` is a projection updated in the same transaction. Enterprise **Internal notes** are labelled "Internal – not visible to developer" and cannot change state. Both parties see a History tab. Daily RFC 3161 stamp over each engagement's chain head. **Messages tab:** one thread per engagement from stage 0/3 onward, parties only, text + scanned attachments, audit-logged, Report button, in-app + email (N18); before stage 3 the org cannot message or see contact details.

### 6.11 Reminders for both sides (reusing the reminder engine)
- Ported `reminder/` policy runs server-side. **Health computed by code only:** `at_risk` if any item is due within 2 BD with no action, a milestone is overdue >0 days, an endorsement awaits a party past its stage deadline, or (only when a repo is linked) no repo activity for `cold_after_days` (default 3 BD) during `IN_IMPLEMENTATION`; `off_track` if any item is overdue >7 days or a rework loop ≥2. Health compares actual progress with the **agreed milestones and dates** from the signed agreement.
- Repository activity comes from a GitHub App (webhooks push/pull_request/issues; read-only contents; Release 2 — Release 1 health is milestone-based); the ported investigator finds "where you left off" and a 15-minute next step. Developers are told at install that repo signals are shared with parties to active engagements, with an opt-out ("no data").
- **Developer daily reminder = EM7/N23** (`reminders.dispatch` every 15 min, sent once at the user's `send_after_hour`, default 07:30 EAT): Needs you / Waiting on other party / Health with code-computed one-line reasons, due milestones, one featured next step, plus one trending problem in their niches (feature-flagged until Phase 5). Haiku 4.5 words it; deterministic `fallback_text` when the LLM fails or budget is spent.
- **Enterprise progress reminder** (org version of EM7, `reminders.org_digest` 08:30, daily or weekly per plan): per engagement On track / At risk / Off track with the code-computed reason, milestones due, endorsements awaiting the org, and "no update from {party} since {date}" when data is missing. Built from code-computed fact tuples only; dev-authored text appears only quoted, attributed and defanged; investigator output never reaches enterprise-facing messages.
