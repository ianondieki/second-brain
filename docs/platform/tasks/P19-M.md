## 1. `engagement_notes` (for P19-A)

The text that a side-state command carries: the organisation's question (`info_request`), the developer's answer
(`info_answer`), the reason of a pause (`hold`) and of an early resume (`resume`). Append-only like the events.

- Columns: `id` uuid pk (uuid7), `engagement_id` fk engagements(id) on delete cascade, `event_seq` int not null (the
  `engagement_events.seq` the note belongs to; unique `(engagement_id, event_seq)`), `kind` text CHECK in
  ('info_request','info_answer','hold','resume'), `body` text not null CHECK (char_length(body) between 1 and 2000),
  `resume_at` date null (set only for `hold`: CHECK (kind <> 'hold' OR resume_at IS NOT NULL)), `created_by` uuid fk
  users(id), `created_at` timestamptz default now().
- Tenancy: ORG_OR_USER like `engagements` (both parties read; `app_engagement_party`-style predicate as the events
  use). INSERT only for bridge_app (SELECT, INSERT); an INSERT-only trigger like `engagement_events` (no UPDATE, no
  DELETE: `tests/integration/test_rls.py` has the append-only pattern).
- The write is done by `commands._apply` in the same transaction as the event, so `event_seq` matches the event that
  the note explains (the chain hash is unchanged: the note is a sibling row, not part of the event).
