# P19-C · In-app notifications: the bell and the Notifications page (spec 07 §1; REQ-NOT-03 in-app channel)

Agent: impl-backend (high) for the API, then impl-frontend for the screens (P19-F). Depends on P19-M (the
`read_at` update grant). `in_app_notifications` (notifications/models.py:59: user_id, org_id, kind, title, body,
link, read_at) is written by `notifications/in_app.post_in_app` from the tracker (`engagements/notify.deliver`),
interest, digests and reminders; nothing reads it back.

## Backend scope

`notifications/in_app_router.py`:
- `GET /api/me/notifications?cursor&unread=1` → newest first, 20 per page (the cursor pattern of the inbox), each
  `{id, kind, title, body, link, created_at, read_at}`; `link` is a platform path (the model's invariant).
- `GET /api/me/notifications/unread-count` → `{count}` (cheap; cached by the client for the bell).
- `POST /api/me/notifications/{id}/read` and `POST /api/me/notifications/read-all` (sets `read_at` where null).
- RLS does the scoping (`Tenancy.USER`); a foreign id is 404.
- Audit nothing (reads); `read` is the user's own state.

`make openapi api-types`. Tests `integration/notifications/test_in_app_api.py`: Given two users with rows, When one
lists, Then only theirs, newest first, unread filter, count; marking read is idempotent; a foreign id 404; a link is
always a path (property test over the writers: every `post_in_app` call site passes a path).

## Frontend scope (in P19-F)

- `components/NotificationBell.tsx` in the top bar (spec 07: portal switcher, bell, avatar menu): an icon button
  with the unread count as a small badge (and in the accessible name: "Notifications, 3 unread"), linking to
  `/notifications`; the count comes with the page (server read) and refreshes after the page's own actions, never
  by polling (JS budget and quiet product).
- `app/(app)/notifications/page.tsx`: a list grouped by day (Today, Yesterday, dates), each row the title, the
  body, the time in EAT, unread marked by a dot and weight, the whole row a link to `link`; opening a row marks it
  read (a server action or the POST on click, then navigate); "Mark all as read" the one secondary action; empty
  state one sentence + one action ("Nothing yet. Your tracker updates and approvals will land here." → Home);
  pagination with the "Show more" pattern of the inbox. Both portals' navigation stays (PortalNavFor).
- Locales en/sw: `notifications.*`, `shell.bell`; `_meta.reviewP19`.
- Tests: unit for the bell (count 0 hides the badge, 100+ reads "99+"), the page (groups, unread, empty), and
  `e2e/notifications.spec.ts`: Given Amina with an approval and a request for information, When she opens the bell,
  Then both rows show, the request first; opening one marks it read and lands on the tracker; "Mark all as read"
  empties the badge.
