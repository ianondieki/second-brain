## The goal

By the end of P28: one container image runs the whole seeded product on one port on any Docker host, in a public-demo
mode where a visitor picks a persona and is signed in with one press, cannot lock other visitors out, cannot upload
files or move the shared clock, sees that the data is fictional and resets nightly, and is not indexed by search
engines; the owner can start a public link from GitHub Codespaces at zero spend in a few minutes, and has a ready
workflow and runbook for a durable host once D-71 is decided. Alongside it, the feature tracks below.

## Track PD — the public demo (REQ-FND-04; D-71)

**Why not simply put it online.** A durable public link needs a host. The research note
(`docs/platform/research/public-demo-hosting.md`, read 2026-10-13) found no host that runs a ~1 GB container durably at
zero spend without a card: Hugging Face Docker Spaces now need PRO (USD 9/month), Fly.io has no free tier, Render and
Koyeb free tiers have 512 MB, Oracle Always Free fits but needs a card for verification. GitHub Codespaces is free on
the owner's existing account but serves only while the codespace runs (idle timeout at most 4 h). Choosing between
spend, a card and an on-demand link is the owner's (CLAUDE.md: any spend or new vendor; D-36), and two open legal
decisions block "any hosted release": D-38 (news excerpts) and D-39 (legal drafts). So this track builds everything that
needs no decision, makes the public mode conservative by default, and records D-71 for the go-live.

**Contract.**
- Settings: `PUBLIC_DEMO: bool = False`; `PUBLIC_DEMO_CONTENT: Literal["fictional", "full"] = "fictional"`. Start-up
  refuses `PUBLIC_DEMO=true` unless `APP_ENV` is dev or test (`DEMO_ENVS`): fail closed, so a production or staging
  process never runs it. The persona router lives in `bridge/demo/` (absent from production images, like the test clock)
  and is mounted only when the module exists and `PUBLIC_DEMO` is true.
- `GET /api/public/demo` (always present, unauthenticated, cacheable 60 s) →
  `{enabled: bool, personas: [{key, name, role: "developer"|"org_admin"|"org_signatory"|"org_reviewer"|"staff",
  detail, home}], reset_hour_eat: 3|null}`; `{enabled: false, personas: [], reset_hour_eat: null}` when off.
- `POST /api/auth/demo/sign-in {persona}` (CSRF as every POST; throttled per IP with the existing throttle, 30 a
  minute) → `SessionResponse` and the session cookie; the session is created with `mfa_pending=false` and
  `mfa_verified_at=now` (so step-up actions work for the persona for ADR-002's 12 h), only for an `ACTIVE` user whose
  `demo_account` is true and whose address is one of the seven (a fixed allowlist in code, not the request); audited as
  `auth.login` with `method: "demo_persona"`. 404 when the mode is off or the module absent; 400 `unknown_persona`.
- Locked routes answer 403 `{"detail": {"code": "public_demo_locked", "message": "This is switched off in the public
  demo."}}` when `PUBLIC_DEMO` is true; one dependency, applied by route, with a test that walks the app's routes and
  fails if a multipart route is not locked.
- The API adds `X-Robots-Tag: noindex, nofollow` when the mode is on; the web reads `PUBLIC_DEMO` at run time (server
  side, never inlined) for its header, `robots.txt` and the banner, and asks `/api/public/demo` for the personas.

**The image and the links (infra; no secrets in the repository).**
- `infra/demo/space/`: one Dockerfile (multi-stage: the backend venv with dev tools, the Next standalone build with

- `.github/workflows/demo-image.yml`: builds the image and pushes `ghcr.io/<owner>/bridge-demo:latest` (and the commit

- `.devcontainer/devcontainer.json`: a codespace built from that image (or from the Dockerfile when the image is not

- `.github/workflows/demo-space.yml` (dispatch only): pushes a two-file Space (`Dockerfile` = `FROM` the GHCR image,

- `docs/runbooks/public-demo.md`: the owner's steps for Codespaces (now, zero spend), Hugging Face (after D-71 (a)),

### The contract (the backend freezes `backend/openapi.json` before the screens start)

**A. Procurement route.**
- States: `PROCUREMENT_ROUTE` joins the engagement state enum between `UNDER_REVIEW` and `INTEREST_CONFIRMED`. When a
  signatory of an organisation with `public_entity = true` approves to proceed, the engagement enters
  `PROCUREMENT_ROUTE` (the named contact person and channel are recorded as today; the contact-by date is not set
  yet). `POST /api/orgs/{org_id}/engagements/{id}/procurement-route {route, justification|null, contact_by}` by an
  `admin` or `owner` of that organisation: `route` ∈ `direct` · `rfq_tender` · `ppp_pip` · `innovation_challenge` ·
  `pilot_mou`; `justification` required for `direct` (20–1,000 characters), optional otherwise (≤1,000);
  `contact_by` at most `contact.contact_by_max_bd` business days ahead of the decision; the engagement moves to
  `INTEREST_CONFIRMED` and the developer's contact details are revealed to the named contact as today. Due:
  `PROCUREMENT_ROUTE: {due_bd: 10}` in `policy.yaml`; no auto-expiry (the spec gives none). A private organisation's
  approve goes straight to `INTEREST_CONFIRMED` exactly as today; the database refuses `PROCUREMENT_ROUTE` for an
  organisation that is not a public entity.
- Read side: `EngagementDetail` gains `procurement: {route, justification, decided_at, decided_by_name}|null` for both
  parties (R46, full transparency) and `steps` includes 3b only for public entities (AC-TRACK-5). History shows the
  decision. The deadlines list (P27) carries the 3b due date; the Board puts 3b in the Contact & NDA column.
- Wording (amended 2026-10-13 after the ux review): the order stays as spec 06 §6.9 row 3 has it (public entities
  enter stage 3 after 3b; the signatory's approval sends the engagement to 3b). The spec's stage name "Procurement
  route determined" read as decided while nobody had chosen, so the product names 3b "Procurement route" (tracker,
  notice titles) and History words the approval into 3b as approved with the route next, not as stage 3 reached
  (`[[COPY-REVIEW]]`). Residual: the route sheet's contact-by date defaults to today, as the approve form's does.
- Seed: a new fixture, State Department D (a public entity, E2; Halima Yusuf owner and admin, Otieno Mwita
  signatory), gets one engagement waiting in `PROCUREMENT_ROUTE` (County Government of C keeps its pending E2 claim,
  so it cannot hold an engagement); the public demo's seventh persona is Halima Yusuf, home `/org`.

**B. Escalations and nudges.**
- A job (the worker, every 15 minutes, on `app_clock_now()`) finds due nudges and records each in a ledger
  (`engagement_nudges`: engagement, kind, key, sent_at; unique on the three) before sending, so each fires once.
  Kinds and rules (business days from the policy, holds and requests for information pausing as for expiry):
  `contact_escalation` (INTEREST_CONFIRMED, +`escalate_bd` 3 → the org's admins and escalation contact; in-app and
  email), `contact_overdue` (the contact-by date passed → EM6 to the named contact and the admins, and EM6's developer
  version to the developer), `nda_reminder` (NDA_PENDING at each of `remind_bd` [2, 4] → each signer who has not
  signed; EM5), `procurement_escalation` (PROCUREMENT_ROUTE at +5 BD of its 10 → the admins and escalation contact),
  `milestone_reminder` (a submitted milestone unreviewed `milestones.reminder_bd` 3 BD → the org's reviewers of the
  engagement) and `milestone_escalation` (`milestones.escalation_bd` 5 BD → the admins and escalation contact).
- In-app always; email per the person's notification preferences (🔒 kinds as the matrix says: EM5 is not mutable;
  EM6 follows the person's settings, docs/spec/06 §6.10 and N05; the milestone reminder is in-app only, N12); templates en and sw, fixed and escaped as REQ-NOT-05 requires; `[[COPY-REVIEW]]` on new wording.
- Read side: `EngagementDetail` for organisation members gains `escalated_at|null` (the latest escalation sent);
  the developer's view does not carry it.

**C. Team.**
- `GET /api/orgs/{org_id}/team` (members): `{members: [{user_id, name, email (admins only), roles, joined_at}]` (the
  repo models no person-level verification; E0–E2 is the organisation's), `invitations: [...] (admins only),
  niche_defaults: [{niche_slug, niche_name, user_id, name}], escalation_contact: {user_id, name}|null}`.
- Invitations (`admin`/`owner`): `POST /api/orgs/{org_id}/invitations {email, roles}` → 201 (a 7-day link emailed;
  the token stored as its hash, as the table already says; at most 20 open invitations per organisation; an existing
  member's address is 409; the organisation must be at least E1 (403 `org_not_verified`); the plan's `seats` count
  covers active members plus open invitations (402 `plan_limit`, re-checked at acceptance); sends are throttled per
  caller, per organisation and per recipient address (429); the email's subject carries no caller-written text); `POST …/invitations/{id}/resend` (new token, the old one dead), `DELETE …/invitations/{id}`
  (revoke). `GET /api/invitations/{token}` (public: the organisation's name and the roles, nothing else; 404 when
  spent, revoked or expired) and `POST /api/invitations/{token}/accept` (signed in, verified email equal to the
  invitation's, case-insensitive → membership with those roles; else 403 `invitation_email_mismatch`). A signed-out
  visitor is sent through sign-in or sign-up and back. Audited.
- Joining by invitation (amended 2026-10-13 after the frontend review's BLOCKER: sign-up forced a developer profile
  or a new organisation, and `/me` puts any account with a developer profile on the developer side, so an invitee
  could get a membership no screen opens). `POST /api/auth/signup` takes an optional `invitation` (the token): with
  `side: "org"` and no `org`, it creates an account with no developer profile, no organisation and no subscription,
  only while that token is an open invitation (else 422 `org_details_required`, as today; `invitation` with
  `side: "developer"` or with `org` is 422 `invitation_conflict`); the address is still checked at acceptance. `/me`:
  an account without a developer profile that is not staff is side `org`, with or without memberships (a removed
  member reaches the organisation screens' no-organisation state, not the developer home). `POST
  /api/invitations/{token}/accept` from an account with a developer profile is 409 `developer_account`: nothing is
  created; the invitation page says so before offering the button (one account, one side, until D-72). Acceptance
  re-checks the seats under the organisation's invitation lock (the security re-check's MINOR).
- Change roles: the existing `PUT /api/orgs/{org_id}/members/{user_id}/roles` (owners; locked in the public demo) is
  offered on the Team page (amended 2026-10-13: the review found it built but not listed here).
- `DELETE /api/orgs/{org_id}/members/{user_id}` (`admin`/`owner`): the last owner cannot be removed or demoted (409);
  open assignments of the removed member are cleared.
- `PUT /api/orgs/{org_id}/niche-defaults {items: [{niche_slug, user_id}]}` (`admin`/`owner`; the user must be an
  active member with the `reviewer`, `signatory` or `admin` role): a new engagement in that niche (on SUBMITTED or
  ORG_INTEREST) is assigned to that member through P27's assignment path (N30 sent as today), unless someone already
  assigned it.
- `PUT /api/orgs/{org_id}/escalation-contact {user_id|null}` (`admin`/`owner`; an active member).
- Public demo: invitations, acceptance, removal and role changes stay locked (Track PD); niche defaults and the
  escalation contact work (organisation settings, wiped at the reset); the page still shows the team.

**D. Transparency and export.**
- `/transparency` (public, server-rendered): the latest signed roots from `GET /api/transparency` (day, root,
  signature, snapshot time), the signing keys, and a short "How to check a certificate against these roots" with a
  link to `/verify`; empty state when no root exists yet; no client JavaScript beyond the shell.
- `GET /api/orgs/{org_id}/engagements.csv` (members; `csv_export` entitlement, else the app's paywall answer, 402
  `plan_limit`, naming the plan that has it; 10 exports an hour per member, 429): UTF-8 with BOM, one header row, columns `reference, title, stage, stage_entered_on,
  due_on, other_party, assignee, procurement_route`, Nairobi dates; formula-injection safe (cells starting with
  `= + - @` or tab/CR are prefixed with `'`); `Content-Disposition: attachment`; audited as an export. The list page
  shows "Export CSV" when the entitlement is on and one muted line naming the plan when it is off. Rows newest first;
  a cut at 10,000 rows says so in `X-Export-Truncated: true`.
