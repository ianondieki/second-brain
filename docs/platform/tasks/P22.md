# P22 — Developer space: Today's five, This week, Peers and team-up

Owner's brief (2026-10-05): three features for developers, a space to find fellow developers nearby in the same field
and work together; a "breakout" space with daily agent-made tech trivia, a leaderboard and learning; an agent that
keeps developers updated on tech events and trends, with calendar booking and email reminders. The orchestrator's
critique (chat, 2026-10-05) cut each to the shape this product's principles allow, and the owner accepted the cuts
("I accept the cuts, write P22 and start P22-A"). Decisions: D-58 to D-62. Branch `claude/fervent-mccarthy-0zyqn2`
→ `claude/eloquent-hypatia-aa3577`. Nothing here changes a MUST requirement or `docs/spec/`; the three are
owner-authorised additions (REQ-DEV-01..03, noted under REQUIREMENTS.md §3 outside the spec's tables; their
acceptance tests are on this card).

## The goal

By the end of P22 a signed-in developer can: take a five-question daily tech quiz with sourced explanations, keep a
streak and join an opt-in weekly leaderboard; see events near them and one trend on Home, add an event to their
calendar in one tap and get a reminder the day before; and find peers in their county and niches by handle and invite
one to team up on a named problem or Brief, with a thread and a collaborator credit on the proposal. With: no agent
acting on anyone's behalf (principle 3); no personal data beyond what the profile already holds (principle 5: county,
never GPS); no new vendor without the owner's decision (D-36); every LLM call under the existing caps and kill switch;
nothing of it visible to organisations.

### A — Today's five (REQ-DEV-01; D-59)

**Why this shape.** Trivia teaches only with a correct answer key and a reason; a model's key is sometimes wrong, so
plain code checks what it can (principle 1) and staff approve the rest before anyone sees it (the research-card
pattern). A public ranking rewards attendance and answer-sharing; a streak rewards coming back, and a weekly, opt-in
board by handle keeps the fun without a permanent league table. Organisations never see any of it (a ranking of
developers would become a proxy for competence).

- **The set.** One `quiz_sets` row per Nairobi day (`quiz_date` unique): `status` draft → approved | rejected,
  `origin` model | seeded, who approved and when, the ledger row of the generating call. Five `quiz_questions` in
  order: a prompt (≤ 300 characters), four distinct options (≤ 120 each), exactly one answer, a "why" (≤ 600), a
  `source_id` from the curated source list and the source's title and URL copied at generation (the list:
  `backend/ai/quiz_sources.yaml`, official documentation pages only, each with host, URL, title and topic; the model
  chooses a source id and never writes a URL, as the research agent cites only the excerpts it was sent), a topic, and
  `status` live | pulled with the reason and moment.
- **Generation.** A worker job at 23:30 UTC (02:30 Nairobi) drafts the next Nairobi day's set when none exists for
  it: one call of a new LLM task `quiz_generation` (Haiku, no tools, `purpose` public, `confidential` false, the
  sanitiser's `injection_suspected` honoured, the caps and kill switch as every task). Checks in code before a draft
  becomes a set (any failure discards the draft and the job tries once more, then gives up for the day with a log
  line): five questions; four distinct options after NFKC and whitespace collapsing; exactly one answer index 0–3; a
  known `source_id`; the lengths; the text rules of `research/checks.py` (no control characters, Latin letters and
  ASCII digits); no question names a private person; no two questions with the same prompt in the last 60 days
  (a prompt hash). The job is idempotent per day and never calls a model when a set exists.
- **Approval.** A staff admin opens `/admin/quiz`: the queue of draft sets (today's first), each question with its
  answer, why and source; Approve or Reject the set (one decision per set, audited `quiz.set_decided`); Pull or
  Restore one question (audited). The developer routes serve only an approved set; a day with none shows "No quiz
  today, back tomorrow". Three flags from distinct established developers (a verified email and at least three finished attempts
  on earlier days; other flags still reach the staff queue) pull a question automatically (plain code) and the set's
  attempts are rescored; staff may restore it, which rescores again, and a question staff restored is never pulled
  by flags again (revision 0009 review).
- **Playing.** `GET /api/me/quiz/today`: the approved set for the Nairobi day (questions without answers until the
  attempt is finished), the developer's attempt state, streak and leaderboard opt-in. `POST
  /api/me/quiz/today/answers` with five answers (0–3 or null) finishes the one attempt per developer per set (a second
  is 409 `already_played`; after the day ends 409 `set_closed`): the score is computed in code from the live questions,
  the answers are stored append-only, the response carries each question's correct answer, why and source. A pull
  rescores every attempt of the set through one definer function (`app_rescore_quiz_set`), the only path that updates
  an attempt. Demo accounts (`users.demo_account`) play but never rank.
- **Streak and board.** `quiz_profiles` (`user_id`, `leaderboard_opt_in` default false, `current_streak`,
  `best_streak`, `last_played_on`), maintained in code when an attempt finishes (consecutive Nairobi days; a missed
  day resets). `GET /api/me/quiz/leaderboard`: the ISO week (Monday–Sunday, Nairobi), the sum of scores of opted-in,
  non-demo developers, ties by total time, top 20 by handle, plus the caller's own points and rank even when not opted
  in (their own data only). `PUT /api/me/quiz/settings` sets the opt-in. The board resets every week; nothing is kept
  of past weeks on the board (attempts stay).
- **Flags.** `POST /api/me/quiz/questions/{id}/flag` with a reason code (wrong_answer, unclear, outdated, other) and
  an optional note (≤ 300), once per developer per question, 10 a day per developer; staff see flags on the set.
- **Who.** Developers only: every `/api/me/quiz/*` route answers 404 to organisation-only and staff accounts;
  `/api/admin/quiz/*` is staff admin. RLS: a developer reads their own attempts, flags and profile only; sets and
  live questions are readable by every developer once approved (answers only through the finish response).
- **Screens.** Home card "Today's five" (`data-home="quiz"`): not played → the one action "Play"; played → score and
  streak; no set → one sentence. `/dev/quiz`: the five questions as radio groups on one page, one primary action
  "Check answers"; then the results with why, source and Flag per question, the streak and a link to the board.
  `/dev/quiz/board`: this week's board, the opt-in switch, the caller's row. `/admin/quiz`: the queue, the set page
  with decisions, flags. No new nav item (principle 6: the developer nav stays at five). Strings in en and sw under
  `_meta.reviewP22a` (`[[COPY-REVIEW]]`, sw `[[SW-REVIEW]]`); copy says "learn", never "compete"/"win".
- **Demo.** The seed writes approved sets of `origin` seeded (drafted by hand in code, like the research cards'
  `SEEDED_ANSWERS`) for yesterday and today, Amina's finished attempts on both (a streak of 2, opted in), Brian's on
  today (not opted in); no model is called; `make check` and the demo never reach a provider.
- **Tests.** P22-A1 generation with fakes: each check rejects its case (duplicate options, two answers, unknown
  source id, over-long why, a private person's name, a repeated prompt), a clean draft becomes a draft set, the job is
  idempotent per day and silent when a set exists, the kill switch and the daily cap refuse the call. A2 approval: a
  draft is never served (404 `no_quiz`), approve/reject by a staff admin only (403 moderator, 404 developer), audited;
  a rejected set is never served and the next job run drafts again for that day. A3 playing: one attempt (409), answers
  validated (422), the score deterministic from fixed answers, correct answers withheld until finished, a closed day
  409. A4 flags: once per developer, 10 a day, only after playing the set; three flags from distinct established
  developers pull the question and rescore every attempt (scores drop for those who had it right; the pulled
  question's row says why); throwaway accounts' flags never pull; restore rescores and is final. A5 the board: weekly
  window on the test clock, opt-in only, demo accounts excluded, ties by time, own row for a non-opted-in caller. A6
  tenancy: organisation seats and staff get 404 on `/api/me/quiz/*`; developers 404 on `/api/admin/quiz/*`; RLS keeps
  attempts, flags and profiles to their owner. A7 streaks on the test clock: consecutive days count, a gap resets,
  best streak kept. A8 the seed: idempotent, nothing on a used demo, the two sets and three attempts present. A9 e2e
  (`frontend/e2e/quiz.spec.ts`): a new developer plays today's five on the demo stack, sees the score and the whys,
  flags one, opts in and sees their handle on the board; axe at 360 and desktop; an organisation member gets no card.

### B — This week (REQ-DEV-02; D-60, D-61) — after A

- **Events.** `events`: title (≤ 120), organiser (the verified organisation that posted it, or "Platform" for staff),
  starts/ends (Nairobi), venue text (≤ 160) and county, or online with a join URL, a description (≤ 1,000, plain
  text), a link (≤ 1 URL, allowlisted scheme), status draft → published | rejected | cancelled, moderated like Briefs
  (staff approve; an E2 organisation's editors post; nothing unmoderated is shown). Shown on Home: up to three
  published events in the developer's county or online, soonest first, this week and next.
- **Calendar.** `GET /api/events/{id}/calendar.ics` (a valid VEVENT, UID stable, Africa/Nairobi) and a Google Calendar
  template link built in code; no OAuth, no agent. **Remind me**: one email the day before (18:00 Nairobi) and one
  in-app notice the morning of (08:00), through the reminders engine and only with the reminders consent; declining
  or the event's cancellation removes both. N26 (email, the day before) and N27 (in-app, the morning of) in the
  notification matrix.
- **Trends.** A research-card type `trend` (the research pipeline with a second source list of official technology
  publishers), staff-approved, labelled, never naming an organisation without an official source; one on Home,
  rotating daily; "Read more" to the card.
- **Tests.** B1 no event appears unmoderated; B2 posting rights (editor roles of E2 organisations, staff; 403/404
  otherwise); B3 the `.ics` validates and the Google link round-trips the time; B4 reminders send once each, only with
  the consent, and never after a decline or cancellation; B5 the Home strip picks county-or-online, soonest, ≤ 3; B6 the
  trend card type passes the research checks and the admin approval; B7 e2e.
- **Defaults taken by the orchestrator (2026-10-06, open to the owner's change).** (1) An event is its own table
  (`events`), not a `problems` row: posting by the Briefs editor roles (owner, admin, signatory, reviewer) of an E2
  organisation, or by a staff admin as "Platform"; staff admins and moderators decide on an `/admin/events` queue
  (its own page like `/admin/quiz`, no `moderation_cases` row), through definer functions as revision 0009 did;
  the poster or staff may cancel a draft or published event; nothing else changes a status. (2) A reader's rights:
  a developer reads published events, an organisation member its own organisation's events in any status, staff
  every event; the `.ics` and the Google link are served for published events only. (3) An event is on one day or
  spans at most three; "this week and next" is Monday of the current ISO week to Sunday of the next, Nairobi.
  (4) "Remind me" is one row per developer and event, removed by Decline; the email (N26, 18:00 Nairobi the day
  before) goes only with the reminders consent and a verified email, exactly as EM7's gate; the in-app notice (N27,
  08:00 the morning of) needs only the Remind me, since in-app is the channel the spec keeps on; the screen says
  which of the two will come. Both are sent once by the `notification_deliveries` key, by a job every 15 minutes
  on the shared clock, and only while the event is published and the reminder row exists. (5) A trend is its own
  table (`trend_cards`, with its sources), drafted by the research pipeline's checks from a second excerpt list of
  official technology publishers (`backend/seed/trend_excerpts.yaml`, allowlist `TECH`), by a weekly job (one call,
  up to three candidates), decided by staff admins on the research page, labelled "Trend · AI-drafted,
  human-reviewed on {date}"; `research_runs` is not used (the card keeps the LLM trace id, as quiz sets do). The
  Home card shows the published trend of the day (rotation by the Nairobi day's ordinal over the published cards),
  with "Read more" to `/dev/trends/{id}`. (6) The organisation portal gains "Events" as its fifth section; the
  admin nav its fifth, "Events". No sixth developer nav item: Home strip, `/dev/week`, `/dev/events/{id}`.
- **Residuals (B, for the owner).** The trend excerpts (`docs/platform/research/trend-excerpts-2026-10.md`, 24
  rows from 14 official publishers) are short dated quotes under D-38's reading; one publisher (Python Insider)
  states a CC BY-NC-SA licence and the others' terms were not reviewed, so the list needs the D-38 legal check
  before release. Safaricom's developer site (bot challenge), ict.go.ke (unreachable), CBK's and KRA's notices (no
  page date or no body) are not in the list; a refresh is a researcher run, never a runtime fetch.
- **MINOR from the B1 review (open).** `trends/checks.py` `_sentence_starts` treats a quoted or bracketed word at a
  sentence start as a name, so `"Developers" should ...` or an all-caps `MUST` is discarded (fails closed; a
  retry or staff see the loss, nothing unsafe passes).
- **Residuals from the B2 and BF reviews (open, MINOR).** No edit of a draft event in the organisation portal (the
  page says cancel and post again); the admin Cancel has no in-place step-up (a stale factor shows a sentence);
  the reminder job's daily sweep lookup reads the job queue's history (prune old jobs or it slows); the admin Trends
  table shows raw topic slugs; the admin events queue has three tabs (In review, Published, Closed) since four did
  not fit at 360 px.
- **Status (2026-10-06):** built and gated; see PROGRESS.md "P22-B report"; A and B merged into the integration

### C — Peers and team up (REQ-DEV-03; D-58, D-62) — after B, once the owner approves D-62's wording

- **Peers.** Opt-in (`developer_profiles.peers_visible`, default false, a switch in settings with a one-sentence
  explanation); `GET /api/me/peers`: opted-in developers in the same county or sharing a followed niche, by handle,
  headline and shared niches, ordered by profile-embedding similarity (the existing `profile_embedding`), 20 a page;
  never an email, phone or name; organisations and staff 404.
- **Team up.** An invitation names a published problem or Brief and carries a note (≤ 300, the contact-details rule
  does not apply between developers; the report and block rules do); accept opens a dev-to-dev thread on the P21
  message rules (append-only, report, block, 60 an hour); a team may attach itself to a proposal as collaborators.
- **Credit.** Per D-62: the registrant stays one person (the certificate's registrant, the engagement's developer
  party); collaborators are listed on the proposal and certificate with the wording the owner approves; the
  originality check runs on the proposal as today.
- **Tests.** C1 opt-in only; C2 county-or-niche, similarity order, no personal data in the payload; C3 invitations
  tied to a real problem or Brief, accept/decline, block ends everything; C4 thread rules; C5 collaborators on the
  certificate exactly as D-62 says; C6 organisations never see peers, teams or threads; C7 e2e.
- **Defaults taken by the orchestrator (2026-10-06, open to the owner's change).** (1) The profile embedding is
  never computed in the prototype (`profile_embedding` is NULL for everyone, T2.1 brings it), so peers are ordered
  by the number of shared liked niches, then same county first, then the newest opt-in; the embedding order
  replaces it when the column is filled, behind the same function. "Shared niches" are the liked ones (`followed`
  is never written). (2) A developer's handle, headline, county name and shared niches reach another developer only
  through SECURITY DEFINER functions over the opt-in flag (the `app_quiz_board()` pattern); never bio, email, name,
  verification level or anything else; a block hides both from each other everywhere. A "counterpart" (reachable
  without the current opt-in) is only the other party of an accepted invitation (a thread) or of a still-pending
  one; a declined, withdrawn or ended invitation counts for nothing, so turning the switch off is always effective
  (the 0011 reviews). (3) New tables:
  `developer_blocks`, `team_invitations` (one open invitation per pair and problem; pending → accepted | declined |
  withdrawn | ended), `team_threads` (one per accepted invitation, between two developers; closed by a block or by
  either party), `team_messages` (append-only, 1–4,000 characters, 60 an hour, report through `moderation_cases`
  with `subject_type = 'team_message'` and the message report reasons), `team_thread_reads`, and
  `proposal_contributors` (the proposal owner adds a thread counterpart; the contributor may leave; handles only).
  (4) Credit per D-62 (a): "Contributors: <handles>" on the proposal page, the certificate sheet and the PDF, read
  from `proposal_contributors` at render time and never part of the manifest (`manifest_version` stays 1, the
  content hash unchanged); nothing about shares; the registrant, the engagement's developer party and the
  originality check are unchanged. (5) Notices: N28 in-app "team-up invitation" and N29 in-app "new team message"
  (in-app only, no email, under the existing in-app channel; a digest or email is a later decision), plus an in-app
  notice when an invitation is accepted. (6) Screens without a sixth nav item: a "Peers" section on developer Home
  (opted in: three peers and "See all"; not opted in: one sentence and "Turn on"), `/dev/peers`, `/dev/teams`
  (invitations and threads) and `/dev/teams/[id]` (the thread on the Messages screen's parts), a third Settings tab
  "Profile" (headline, county, the peers switch with its one sentence: "Developers in your county or niches can see
  your handle, headline and shared niches. Never organisations."), the contributors line on the idea page and
  the certificate. (7) Organisations and staff get 404 on every peers and teams route; staff read a reported team
  message through the moderation queue only.
- **Residuals (C, open, MINOR).** The blocked party can infer a block from a thread that closed as `ended` with no
  counterpart card (a who-left column and a handle snapshot on the thread would hide it: a later revision); the
  composer counts attachments from the list as it was when the file was picked while the attach code is still
  loading (the API enforces the limit); `/dev/ideas/<id>` has 494 B of budget headroom and `/dev/teams/<id>`
  about 1,200 B; the profile embedding is still never computed, so peers order by shared niches and county only;
  Contributor "Leave" sits on `/dev/teams` under "Credited on", not on the thread; invitations answered in
  another tab show on the next read.
