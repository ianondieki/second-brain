   shared niches and county, Recommended-for-you's f1 is a keyword share, and the originality check is the only
   vector use. Compute it from headline, bio, liked niches and the developer's published teasers with the existing
   embedding path (bge-m3 behind the LLM layer's fakes), on profile change and nightly; then `app_peers` orders by
   cosine as the card intended. Needs: a revision (index), the reembed job's profile plug-in, evals. REQ-DEV-03,
   REQ-REC-01.
2. **One nav home for the developer-space features.** Today's five, This week and Peers each live on Home plus
   their own routes; a developer finds `/dev/peers` and `/dev/teams` only from Home and the notices. Without a
   sixth nav item (principle 6): a "Today" grouping on Home with the three sections in one rhythm, and a small
   "Your space" row of links under the Home header. Measure with the tour and the e2e.
3. **Invitation and thread liveness.** `/dev/teams` reads itself after an answer, but a thread does not update while
   open (a second party's message appears on reload), and an invitation answered in another tab shows on the next
   read. A cheap poll of `unread-count` every 60 s on the thread and the teams page (no sockets, no new vendor).
4. **Event drafts.** An organisation cannot edit a draft event (cancel and post again). A draft edit form on
   `/org/events/[id]` with the backend's existing PUT; the admin queue then shows "edited since you opened it" via
   `seen`.
5. **The blocked party's inference** (P22-C residual): a who-left column and a handle snapshot on `team_threads`
   (revision 0012) so a block reads exactly like a leave; the composer's attachment count while its code loads.
6. **Trend topics and the admin Trends table**: labels for the eight topic slugs (en/sw), the raw slug gone;
   the admin Cancel on events with an in-place step-up like the decisions.

## P23-3 — The deadline countdown: days, hours, minutes (2026-10-07; REQ-TRACK-03, REQ-DEV-01, REQ-UX-01)

The owner: "add the project submission dashboard closes timer with days, hours, minutes to help the developer be
alert with the project he is currently doing for a particular company."

**Defaults taken by the orchestrator:**

1. **What counts down.** The engagement's current step deadline (the tracker's `due`, by the end of the due day in
   Nairobi) and a Problem Brief's submission deadline ("Proposals by …"). The countdown says time left to that
   instant in days, hours and minutes; the existing "in n business days" wording stays beside it (the API's own
   figure), so the two never disagree about what the deadline is.
2. **Where.** The developer Home's "Next deadline" tile (the countdown as the tile's meta line, the business days in
   its title) and the "Needs you" card (under the date); the engagement tracker's deadline line (both sides see it:
   the organisation's turn has a deadline too); the problem page's Brief deadline ("Submissions close in …"). No new
   screen, no new nav item, no notification (the reminders engine already covers N-series deadline notices).
3. **The clock.** The API stamps every response with `X-App-Now` (the app clock, so `make demo-clock` and the test
   clock move the countdown too) and `DueOut` gains `due_at` (the instant the window closes); the Brief's deadline
   gains the same instant. The page renders the first value on the server from `X-App-Now`, then ticks once a
   minute from that offset in a client component of a few hundred bytes; never the browser's clock alone.
4. **Honesty and accessibility.** A `<time>` element with the full instant in its `dateTime` and title; no live
   region (a ticking countdown must not be announced); the figure in tabular numerals; a warm (saffron) tone with
   the "Your turn" mark only when under 24 hours remain and the step is the developer's; past the instant the
   existing wording ("Overdue", "Closed") replaces the countdown; en/sw unit strings; no sideways scroll at 360; the
   page keeps its one primary action.
