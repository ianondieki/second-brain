### A — Messages (REQ-ENG-11; spec 06 6.9 "Messages tab", AC-TRACK-9, N18)

- **Who.** The parties only: the engagement's developer, and the organisation members the tracker already lets act
  or read on it (the same visibility as `tracker_engagement_visible()`). Staff read a message only through a report
  case (the reporter shares that one message), never the thread.
- **When.** Posting opens once the chain has entered `INTEREST_CONFIRMED` or any later main-path state (`CONTACT_MADE` on a public entity's procurement route counts; `PROCUREMENT_ROUTE` itself does not) and stays open through the deal states; it closes (read-only) at
  `CLOSED`, `DECLINED`, `WITHDRAWN`, `EXPIRED`, `TERMINATED`. Before `INTEREST_CONFIRMED`: the organisation's GET and
  POST are 403 (AC-TRACK-9); the developer sees an empty-state sentence saying when the thread opens.
- **What.** Text 1–4,000 characters, plain text only (no markup rendered, links shown as text and never auto-linked
  for the other side; the API never interprets them). Up to 5 attachments per message, each ≤ 20 MB, stored in the
  existing object store and scanned by `storage/scanner.py` (`pending` → `clean` / `infected`); only `clean` files are
  downloadable, by parties only, through a short-lived signed link; an infected or failed scan is final (the sender uploads again). Object keys are `messages/<engagement>/<attachment>` (a CHECK); staged uploads that can never be sent (the engagement ended, or older than 24 hours) are purged hourly.
- **Record.** Append-only (no edit, no delete; UPDATE and DELETE refused for every runtime role, as `engagement_notes`
  in 0006). Each post writes an audit event. A body's erasure follows D-54's default (a): a later staff-only definer
  function may redact a body; none exists yet. Messages are not part of the hash chain (the events are).
- **Report.** A party reports a message (one report per reporter per message) → a moderation case with
  `subject_type = 'message'` carrying that message's text and sender role (the reporter shares it); the message stays
  visible to the parties. Reason codes only (spam, abuse, contact_details, confidential, other), at most 10 reports
  a day per user (fixed in the database). Every staff read of a reported message is audited.
- **Notify (N18).** In-app always (the bell). Email (a status email, mutable in notification settings): at most one per
  recipient per engagement per 30 minutes; it says who wrote and links to the tab, never the message text (the text
  may hold contact details or confidential detail; email is the weaker channel).
- **Limits.** 60 messages per user per hour per engagement (429 with a retry-after); an empty or over-long body 422.
- **API.** `GET/POST /api/engagements/{id}/messages` (cursor pagination, newest last), `POST
  /api/engagements/{id}/messages/{mid}/report`, attachments: `POST …/messages/attachments` (upload, returns an id to
  send with the message) and `GET …/messages/{mid}/attachments/{aid}` (a signed link). Unread: a per-member
  `last_read_at` for the thread; `POST …/messages/read`.
- **Tests.** P21-A1 AC-TRACK-9 both halves (`integration/engagements/test_messages_gate.py`, the name REQUIREMENTS
  plans). A2 a non-party (another organisation, another developer, staff) gets 404 on the thread and attachments. A3
  read-only after each terminal state (409). A4 infected attachment refused, pending not downloadable, clean
  downloadable by both parties only. A5 append-only: UPDATE/DELETE refused for the app role. A6 report creates one
  case with the text; a second report by the same user is idempotent. A7 N18: in-app always, email throttled to one in
  30 minutes, no message text in the email, muted when the recipient turned it off. A8 the History tab lists message
  entries for both sides.

### B — Shortlist and compare (REQ-REPO-02)

- **Who.** Organisation members with a Tier-2 role (reviewer, signatory, admin) add and remove; every member reads.
  Organisation-scoped (RLS on `org_id`, the tenancy pattern); another organisation never sees it.
- **What.** One row per (organisation, proposal); `added_by`, `added_at`; a proposal can be shortlisted only if this
  organisation can already see it in its Inbox (pitched to it, matched by its scout, or answering its Brief), else 404.
  Removing is allowed (a shortlist is a working list, not a record; the audit log keeps add and remove).
- **Compare.** 2–4 shortlisted proposals side by side: title, niche, county, stage (maturity), what the developer is
  looking for (ask), the certificate's registration date, the engagement's stage if one exists, and the scout's fit
  band if matched. **Tier 1 only**: compare never shows Tier-2 text, even for proposals whose NDA the organisation
  accepted (the full proposal stays one click away, with its watermark and view log).
- **API.** `GET /api/orgs/{org}/shortlist`, `PUT/DELETE /api/orgs/{org}/shortlist/{proposal}`, `GET
  /api/orgs/{org}/shortlist/compare?ids=…` (2–4, all shortlisted, else 422).
- **Tests.** B1 add/remove by reviewer; viewer reads but cannot add (403). B2 another organisation cannot read or
  add (404, RLS). B3 a proposal the organisation cannot see cannot be added (404). B4 compare 2–4 only, Tier-1
  fields only (a test asserts no Tier-2 field name in the payload). B5 audit events on add and remove. B6 the Inbox
  shows the star state for each row.

### C — Saved searches and alerts (REQ-PERS-03, REQ-TREND-02)

- **Who.** A developer (any plan); up to 10 saved searches.
- **What.** A name (1–60 characters) and the Discover query: view (`problems` or `briefs`), niche (slug), county
  (code), words (≤ 100 characters). `alerts` on by default; `last_alerted_at`.
- **Alerts.** A daily job at 07:05 Nairobi (04:05 UTC) finds, per saved search with alerts on, the problems or
  Briefs **published** since `last_alerted_at` (or since it was saved) that match and that the developer may see; if
  any, one in-app notification per saved search ("3 new problems match Agriculture in Nakuru", linking to Discover
  with the filters applied); with the developer's opt-in (notification settings, off by default), the day's matches
  go in one status email listing the saved searches and counts, never problem text. Idempotent per day: a re-run on the
  same day sends nothing new (the job advances `last_alerted_at` in the same transaction as the notification).
- **API.** `GET/POST /api/me/saved-searches`, `PATCH/DELETE /api/me/saved-searches/{id}` (name, alerts).
- **Tests.** C1 CRUD and the cap of 10 (409 on the 11th). C2 owner-only (another user 404). C3 the job notifies once
  per saved search with the count of new matches, none when zero, never twice for the same item. C4 alerts off and
  deleted searches send nothing. C5 only published, visible items count (a held problem or a closed Brief does not).
  C6 the email opt-in: off by default; when on, one email per day, counts only.
