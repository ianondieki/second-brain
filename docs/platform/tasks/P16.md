## What was built

**`/settings/notifications`** (signed in, either side; every email footer's "Manage notifications"; avatar menu
"Notifications"). One checkbox per notification consent from `GET /api/me/consents`, grouped by channel: Email
(`reminders`, `marketing`) and WhatsApp (`whatsapp`). Each label is the API's wording verbatim. "Save choices" is the
one primary action; a save sends `PUT /api/me/consents` with only the changed decisions, each on the version shown.
WhatsApp is not available yet: its box is disabled with a one-line reason, unless the person opted in at signup, in
which case it can be turned off (withdrawal stays possible) but never on. Refusals are fixed sentences, never the
API's message: 409 `consent_text_changed` ("The wording of these choices changed after you opened this page, so
nothing was saved." → Reload the page), 401 (→ Log in), 429, network and any other failure. The refusal takes focus;
the saved confirmation is in a live region that is always on the page.

Purposes the settings API lists that are not offered here, and why: `profiling` (P12-F puts its toggle with the liked
niches on `/dev/discover/niches`; not duplicated, docs/spec/07 does not place it here), `github_import` (asked at
GitHub connect, Release 2), `tier2_llm_moderation` (per proposal, docs/spec/06 6.12). `tier2_llm_assistant` is never
listed by the API (per sign-in, REQ-PROP-05).

**`/help`** (public, so an email link opens signed out; signed in, it has the account menu; the API being down never
blocks it). Four sections: how pitching works, what stays confidential (Tier 1 teaser and Tier 2 details in the
approved access, logging and evidence phrasing of docs/spec/04 principle 2), reminders (link to the notification
settings) and support ("Support contact to be set.": no address or phone). No primary action and no script of its
own. All copy `[[COPY-REVIEW]]` (`_meta.reviewP16a`); Swahili drafts `[[SW-REVIEW]]`.

**Avatar menu**: Plan & billing, Notifications, Help, then Sign out.

**Dates**: `lib/format.ts` is the one formatter: "30 Sep 2026" for a day and "30 Sep 2026, 14:06" for a moment (the
language's own separator, from Intl), Nairobi time, "Sep" never "Sept" (en-KE writes "Sept"; the month comes from
en-US's short names, as the tracker did). The tracker's `eatParts`/`formatDate`, the idea list and page
(`dev/ideas/dates.ts`), the organisation screens (`org/format.ts`) and the problem card and staff research screens
(`problem.ts`) all go through it. The long form "29 September 2026 at 14:06" (NDA acceptance, registered at, who has
seen this) is now "29 Sep 2026, 14:06"; the problem label's "30 September 2026" is "30 Sep 2026".

**`test_web_paths.py`**: `/settings/notifications`, `/help`, `/billing/upgrade` and `/org/inbox/matches/{}` leave
`PAGES_NOT_BUILT` (now empty); `test_no_page_is_listed_as_not_built` fails on a stale entry and
`test_the_email_footers_and_the_upgrade_link_are_pages` pins the four links. Mutation-checked: "/help" put back in the
list fails the stale test; removing the help page fails the link tests.

## Open items (P16-A)

1. The visual polish pass (skill chain, Lighthouse) is deferred to the later P16 pass; the layout follows the existing
   screens (Plan & billing, Security).
2. A signed-out reader opening "Manage notifications" from an email lands on `/login` and, once signed in, on their
   home, not back on the settings: `/login` has no return path. A safe `next=` (as `lib/billing/upgrade.ts` does for
   checkout) would fix it.
3. Per-kind preferences (`notification_preferences`, read by `reminders/dispatch.py` `channel_enabled`) have no API,
   so the page offers the consents only. REQ-NOT-03 ("email per preference") needs `GET|PUT /api/me/notification-
   preferences` before the page can offer per-kind choices.
4. `tier2_llm_moderation` is persistent and listed by the settings API, but no screen lets a person give or withdraw
   it yet (docs/spec/06 6.12 places it per proposal); `github_import` waits for GitHub connect (Release 2).
5. `profiling` lives on P12-F's `/dev/discover/niches` (developers). An organisation member who ticked it at signup has
   no place to withdraw it; if the owner wants one place for every consent, a "Privacy" section could list it here too.
6. Support contact: "Support contact to be set." until the owner sets one (`help.support.body`); no address or phone
   is invented.
7. `/verify` keeps its long certificate form ("29 September 2026 at 14:06:25 Nairobi time", seconds included) to match
   the certificate; change it with the certificate PDF if one format is wanted there too.
8. docs/spec/07 names the menu item "Notification settings"; the menu and page title say "Notifications" (the
   orchestrator's wording). `[[COPY-REVIEW]]`.
9. There is no settings navigation between `/settings/security` and `/settings/notifications`; each is reached from
   the account menu (Security from Home's two-step card). A settings nav is a later design choice.
10. The EM1 footer's links are checked end to end; EM2, EM3, N17, the nudge and the org digest build the same two
    links (`test_web_paths.py` pins them as pages) but are not opened from those emails in the e2e.
