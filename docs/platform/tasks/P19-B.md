# P19-B · Problem Briefs backend (REQ-DIR-05)

Agent: impl-backend (high). Worktree. No schema change: `problems` (`source='org_brief'`, `org_id`), `problem_briefs`
(visibility, budget_band, deadline, status), `brief_invitations`, their RLS, grants and the plan limit
`problem_briefs` (claimed 1, starter 5, growth unlimited) exist (0002, `plans.yaml`). Map: scratchpad
`p19/map-briefs-directory.md`. Spec: `docs/spec/06` §6.2 last bullet, §6.5 ProblemCard, §6.12 moderation, 05 plans.

## Scope

New module `problems/briefs.py` + router `problems/briefs_router.py`, prefix `/api/orgs/{org_id}/briefs`, roles as
the RLS editor set (owner, admin, signatory, reviewer) through `tenancy.deps.org_member(...)`.

- `POST /` creates a brief in one transaction: a `problems` row (`source='org_brief'`, `status='pending_review'`,
  `moderation_state` from the same pre-screen developer problems use, `created_by`, `org_id`) and a `problem_briefs`
  row (`status='draft'` → `'published'` is set by the org only when the problem is published; see below), then
  `open_case(db, "problem", id, [...])` so staff see it in the moderation queue. Fields: `title` (≤ 90), `statement`
  (≤ 1200), `affected_group` (optional, as the ProblemCard), `niche_id`, `county_code` (optional), `budget_band`
  (a code from `config/matching/weights_v1.yaml` bands, optional), `deadline` (date, optional, ≥ today),
  `visibility` (`public` only in P19: `invited` → 422 `visibility_not_available`). Refusals: E1 or unverified org →
  403 `verification_required` (E2 only, as the RLS says); plan cap → 402 with the entitlement payload the scout
  router uses (`check_count(..., "problem_briefs", used=open briefs)`), under the same advisory lock; 422 codes for
  bad band, past deadline, long text; the sanitiser's contact-detail rule applies (no emails/phones in a brief).
- Publication: staff approve the problem in the moderation queue (`app_moderate_problem`); when a brief's problem
  becomes `published`, the brief row becomes `published` (do it in `admin/moderation.py` where the problem is
  published, or in a trigger-free service call there: one place). The feed (`trend_facts.py`) already requires both.
- `GET /` lists the org's briefs (any status, newest first, with `problem.status`, `moderation_state`, counts of
  proposals linked: `proposal_count` from the existing link table), `GET /{problem_id}`, `PATCH /{problem_id}`
  (budget_band, deadline while not closed), `POST /{problem_id}/close` (`status='closed'`: it leaves the feed; the
  problem stays published for the proposals already linked).
- Developer side: `GET /api/problems/{id}` and the Discover feed label a brief "Posted by {org}" (`LABELS` +
  `ProblemRef.org: OrgRef | None` with id, slug, name; no personal data); a new Discover view `briefs`
  (`GET /api/discover/briefs?niche&county`: published, open briefs, newest first, with `budget_band`, `deadline`,
  the org ref and the proposal count); `startProposalHref` for a brief adds `&org=<id>` so the editor's pitch step
  can pre-select the organisation (frontend reads it; backend: `GET /api/problems/{id}` returns `brief: {org,
  budget_band, deadline}` when the problem is a brief).
- Entitlement wording: `[[COPY-REVIEW]]` strings in the API error payloads follow the scout router's pattern.

## Decisions taken (impl-backend, 2026-10-02)

1. **Where the Brief row is published.** Revision 0002 lets only the organisation's editors write `problem_briefs`
   (UPDATE `USING _ORG_EDITOR`; staff are not members, and `app_moderate_problem` touches `problems` only), so
   `admin/moderation.py` cannot set the Brief `published` at approval without a policy change, and no schema change is
   allowed here. Thinnest honest option: the E2 organisation writes its Brief row `published` when it posts (RLS
   checks E2); the problem stays `pending_review` until staff publish it, and every developer-facing read (`problems`
   RLS, the Briefs view, `trend_facts`, the ranker) requires the problem published and clear, so staff approval is
   still the only thing that makes a Brief visible. `draft` is unused. Residual: a pending or rejected Brief's
   `problem_briefs` row (ids, band code, deadline; no text) is readable by any signed-in user at the database level;
   the API never reads it without its published problem. If wanted, `db-migrations` can let `app_moderate_problem`
   publish the Brief row; Briefs are then created `draft` (one line in `briefs.py`).
2. **Closing (open question).** `problem_briefs` SELECT shows a non-member only `published` Briefs and `problems`
   SELECT shows an organisation's problem only through a visible Brief, so after closing, the problem page and its
   link on proposals are readable by the organisation's members and staff only: developers get 404, and the link
   drops from public teasers. "Keeps the problem page" holds for the organisation; for developers it needs a
   `db-migrations` change (`status IN ('published', 'closed')` in the public branch of the `problem_briefs` SELECT
   policy). The test asserts what holds today.
3. **Open Briefs** (the plan cap's `used`): not closed and the problem `pending_review` or `published`; a rejected or
   archived Brief frees its slot.
4. **Briefs view**: published and clear, public, not closed, deadline today or later (Africa/Nairobi on the platform
   clock; a passed deadline leaves the view, not the problem page); inner join on the organisation (a delisted one's
   Briefs leave the view); paged with `limit`/`cursor` like the other lists.
5. **Refusal shape**: 422 `invalid_brief` with `errors[{field, code, message}]` (the proposal editor's shape); codes
   `blank`, `too_long`, the sanitiser's `contains_*`, `unknown_niche`, `unknown_county`, `unknown_budget_band`,
   `deadline_past`. Request models refuse only absurd sizes, so lengths answer with a code.
6. **`state`** (in_review | published | rejected | closed) is derived in code for the organisation's list, beside the
   raw `status`, `problem_status` and `moderation_state`.
7. **Files**: the card's `problems/briefs.py` (the organisation's service) and `problems/briefs_router.py`, plus
   `problems/brief_rules.py` (the plain-code rules: text, state, band) and `problems/brief_schemas.py` (shapes, as
   `matching/discover_schemas.py`); `GET /api/discover/briefs` is `matching/discover.py::briefs_view` in the Discover
   router; `sanitise.contact_codes` is extracted so Briefs reuse the contact rule unchanged.
8. **Moderation queue** shows `affected_group` for problems: a Brief's is public text staff must see before approving.
9. `ProblemRef.org` and `ProblemDetail.brief` default to null, so they are optional in OpenAPI and the existing
   frontend fixtures typecheck; responses always carry them.
10. Reads (list, one) are open to any member, as scouts; writes to the editor set.
